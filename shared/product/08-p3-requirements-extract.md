### 1.2 业务规则原文（要点）

- **72h 默认接受**（D38/D40）：`入库时间 ≥ 72h 且状态=待WA确认 → 后台 worker 改状态=已确认 + auto_accept=true`（05 §4.2）
- **异议即时冲销**（D39）：WA 异议 → 库存**即时反向冲销（一条反向流水）**，单据「争议中」，TA 仲裁（04 §1.1 约束）；对应架构接口 `InventoryService.reverseInboundForDispute(inboundId)`（02-modules §2.5）
- **计费联动**（US-WK-01b）：「待确认」期间正常计费（起算次日 0:00）；异议冲销时反向流水**截止于异议日**；TA 仲裁通过 → 恢复入库流水（**视同新入库**，重新起算？原文"恢复入库流水(视同新入库)"，计费口径需架构确认）；仲裁驳回 → 保留冲销、单据「已撤销」、货物 WA/WK 线下处理
- **前置条件**（05 §4.2）：WK 代建入库要求归属 WA ∈ 本店已入驻列表；[拍照=必填] ≥1 张；[批次=启用] 批次号+保质期已填；登记即同时生成入库流水 + 进「待WA确认」队列
- **入库照片**（05 §11）：≤5 张/单据、单张 ≤5MB、永久保存；分桶：批次启用含 `batch_id`，关闭含 `inbound_id`
- **展示图同步**（02-modules §8）：`InboundRegisteredEvent → product 展示图源同步`；`PhotoSwitchedEvent → SKU 展示图源回退`
- **数量差异**（04 §3.1）：实物差 ≤5% WK 按实物登记备注差异不驳回；>5% 驳回 R2

### 1.3 状态机（04 §1.1）

```
[*]→待受理 (wa_submit) →已撤回(R1) | →已驳回(R2) | →已受理 →已入库 →已纠错(R3,≤24h,TA审批)
[*]→待WA确认 (wk_created 登记即生效) →已确认(WA接受 | 72h auto_accept)
待WA确认 →争议中(WA异议,库存即时反向冲销) →已确认(TA仲裁通过,恢复流水) | →已撤销(TA仲裁驳回,保留冲销)
不可达：已驳回→已受理 ❌；已入库→已撤回 ❌（05 §4.1）
```
关键约束：待受理→已受理时**锁单**防 WA 二次撤回；已受理→已入库拍照按开关；已入库→已纠错仅 24h 窗口。

### 2.2 业务规则原文（要点）

- **不可异议**（04 §1.2）：货已离仓不可逆补回；WA 端「已确认（代建）」队列仅作通知（含代建人/SKU/件数/出库照片/收货人）；客诉仅状态转「客诉中」，**OPS 仲裁仅判责不改库存/账单**
- **仲裁结论枚举**（05 §4.2）：「WK 责任 / WA 责任 / 双方协商 / 无责」，任何结论都只作线下赔偿依据（平台不接资金）
- **客诉时限**（05 §4.2）：单据状态=已出库 且 source=wk_created，**30 天内**可提
- **大额校验**（05 §4.2 + 06 §3.5b）：单笔件数 > 在库 50% → 必经大额弹窗 + **复述件数**必填
- **计费**：出库流水正常落库，按出库日截止本批次计费（当天含，05 §1.2）
- **托盘释放**（05 §3.3）：`ceil(占用托盘 × 出库件数 / 入库件数)`，WK 可手动覆盖；批次关闭时按均值反算仅作提示值
- **留痕强化**（US-WK-02b）：原始截图、设备、代建人、归属 WA 全记录

### 2.3 状态机（04 §1.2）

```
[*]→待受理 (wa_submit / inquiry_auto) →已撤回(R4) | →已打印(WK打印)
已打印 →已撤销(R4,需WK二次确认;意向单来源联动回滚) | →已出库(登记) | →待受理(WK重新核对回退)
[*]→已出库 (wk_created 直达，跳过所有前置态)
已出库 →已纠错(R6,≤24h,TA审批) | →客诉中(WA事后客诉) →已出库(OPS仲裁,库存/账单不变)
不可达：已出库→已撤回/已撤销 ❌；已撤销→已出库 ❌
```

## 三、T3 · 退货单 + 盘点单

### 3.1 退货单（R5 / US-WA-R03）

- **流程**：WA 提交（指定批次+件数）→ WK 受理 → 现场出货登记 → 「已退货」（S7 链路）
- **状态机**（04 §1.6）：`待受理 → 已撤回 | 已受理 → 已退货`（最简单据，无审批）
- **规则**：库存按件+托盘扣减；仓储费**累计到退货日当天截止**（05 §1.2）；退货数量 ≤ 该批次当前在库数；仅在库>0 的批次可退（05 §14b.10）；退货不影响 RT 意向单流转；退货流水为独立类型（05 §3.2）
- **单据号**：`RT-{tenant简码}-{YYYYMMDD}-{6位}`（05 §7.1）⚠️ 前缀 RT 与终端角色缩写撞名，建议 P3 改（如 RTN）
- **线框**：❌ **全缺** —— WA 单据 Tab 有「退货申请」菜单项（03 §4.5），但退货表单、WK 受理页、退货详情均无线框
- **权限**：WA 发起（01 §4.3 无独立行，归入单据域；R5 触发方=WA，WE 未提及 → 需明确 WE 是否可发起退货）

### 3.2 盘点单（US-WK-03，决策 D22–D25）

- **流程**（S10）：WK 现场盘点录实物数 vs 系统数 → 差异自动标盘盈/盘亏 → 提交 → **TA 审批（全部差异，无自动通过阈值，D23）** → 通过后逐条生成盘盈/盘亏流水 → 库存+计费联动
- **状态机**（04 §1.5）：`草稿 → 待审批 → 已驳回(→草稿改正重提) | 已通过`；**已通过不可逆**（05 §4.1）
- **核心规则**：
  - 盘盈/盘亏 = **独立流水类型，不修改原入库流水**（D22，审计链保留）
  - 库存公式：`库存 = 入库 - 出库 - 退货 + 盘盈 - 盘亏`（05 §3.1）
  - 批次启用：按 SKU+批次盘；**盘盈必填新批次号+保质期（D24）、盘亏必填指定扣减批次**；批次关闭：按 SKU 总数盘，盘盈并入总库存
  - 计费联动：盘亏件盘点日（=审批通过日）截止、次日不再累计；盘盈件次日 0:00 起算视同当日入库（05 §1.2）
  - **不生成赔偿单**（D25，平台不接资金），线下协商
  - 月度账单需含本月盘盈/盘亏计费影响明细行 ← **P4 依赖点**
- **并发约束**（04 §6.1）：盘点单审批生成流水时对涉及批次**加行锁**，拣货等待
- **线框**：✅ WK 新建盘点单（06 §3.6，批次双分支）+ TA 审批中心/审批弹窗（06 §2.3，含联动影响提示）；❌ 缺：盘点单驳回后 WK 改正重提页、盘点历史列表
- **权限**：库存盘点/差异调整 WK ✅、TA 🔵兼任，其余 ❌
- **99 未决**：无直接条目；**边界缺口**：盘亏指定批次在审批等待期间被出库出完 → 审批通过时流水如何落？（04 决策表未覆盖，需产品补充）

## 四、T4 · 批次管理 + 临期预警 + 强制清库 + 开关联动

### 4.1 用户故事

| 编号 | 摘要 |
|---|---|
| US-TA-12 | 批次管理总开关（默认关闭）；关→启弹窗确认+生成默认批次占位；启→关弹窗确认+老批次出完为止 |
| US-WK-04 | 临期预警：按剩余天数排序列表，一键站内信通知 WA |
| R19 (US-WK-R04) | 强制清库：每日扫描到期批次自动标「待清理」→ WK 发起清库单+拍照凭证 → TA 审批 → 库存清零、计费截止；WA 站内信含凭证照片 |

### 4.2 业务规则原文（要点）

- **FIFO 三算法**（05 §2）：启用=`到效期 ASC → 入库时间 ASC → batch_id ASC`；关闭=按入库时间总数扣减；**混合（启→关切换期）=先老批次后无批次库存**
- **指定批次出库**（05 §2.4）：批次启用时 WA 可指定；缺货时提示 FIFO 替代由 WK 选择；批次关闭时隐藏
- **拆批**（05 §2.6）：一笔出库可跨批次落多条流水
- **临期判定**（05 §9.1）：`到效期 - 当日 ≤ 临期阈值`（TA 设，默认 30 天）；FIFO 选中临期批次时拣货页标「临期 N 天」不阻塞（05 §2.5）
- **强制清库**（05 §9.3）：`保质期-当日 ≤ 0 → 自动标"待清理"`；清库单**必附实物照片，不受拍照开关影响**；生成「临期清库」类型流水，件数=批次剩余；计费截止清库日；**不计入正常出库统计**但在库期间仍计仓储费
- **批次号**（05 §7.2）：WA 自定义，唯一约束 `(wholesaler_id, sku_id, batch_no)`；默认批次占位 `DEFAULT-{YYYYMMDD}`、保质期 NULL 可补录
- **开关联动**（04 §3.8 + US-TA-12）：
  - 关→启：每个 in_stock>0 的 SKU 自动生成默认批次，FIFO 时间戳=切换时刻
  - 启→关：老批次保留独立库存出完为止；新入库不录批次；临期预警停用（已生成的预警/清库单继续处理完）；展示图"入库实拍"改按"最新一次入库"取
  - 进行中的入出库单**按提交时开关策略走完**；切换频次 **24h ≤ 2 次**；切换 1 分钟内全店生效+日志
  - 架构落点：`BatchSwitchedEvent → inventory`（默认批次生成/临期停用），副作用集中 `BatchService.handleSwitchEvent`（02-modules §2.5/§8）
- **定时任务**（04 §4）：每日 02:00 临期扫描、02:30 保质期归零标记；失败重试
- **Batch 状态**（03 §3.4）：在库/已售罄/已退/临期/已清库

## 七、对 P1/P2 已建代码的依赖与冲突点

> 核查基线：main（Flyway V1–V9）+ feat/p2-onboarding（V10__init_onboarding.sql 已占用）。

### 7.1 迁移与版本

- **Flyway V10 已被 P2 入驻占用** → P3 从 **V11** 起编号
- 错误码：P2 用 50201–50205 + 溢出 50310+；main 枚举已占到 50306 → **P3 新码从 50310+ 之后与 P2 对齐排段**（建议 document 异常链 50320+、批次/临期 50340+，落地时与 P2 合并后统一）

### 7.2 批次开关：P1 已有开关字段但**无任何行为**（最大改造面）

- `tenants` 表 V2 已有 `batch_enabled TINYINT DEFAULT 0` + `photo_mode VARCHAR(16) DEFAULT 'NONE'`；`StoreSettingsDto`/`TenantSettings` 已透出 → **TA 现在就可能把 batch_enabled 改成 1，而库存/单据完全忽略它**（V6 注释明确"批次关闭模式"）。P3 落地前存量租户的开关值与数据形态可能已不一致——建议 P3 第一波先做"开关值校准 + 未实现前禁改"防御
- `inventories` 唯一索引 `(wholesaler_id, sku_id)` 单 SKU 维度 → 批次启用需新增 `batches` 表 + 库存行按 `(sku, batch)` 拆分 + **存量数据迁移生成 DEFAULT 批次**；混合 FIFO（05 §2.3 老批次出完为止）实现复杂
- `stock_movements` 仅 `type`(INBOUND/OUTBOUND)/`qty`/`ref_doc_no`，无 `batch_id`、无托盘变化列 → V11 加列 + type 扩 `RETURN/GAIN/LOSS/EXPIRY_CLEARANCE`（05 §3.2 六类）；**库存公式（05 §3.1）是 P3 全部单据的共同不变量**，盘点冲销/异议冲销/退货全都只能走"新增反向/独立流水"，禁止 update 原流水（D22 同理适用）

### 7.3 单据域：P1 是"直达终态"极简版，P3 引入全状态机属**结构性重构**

- `inbound_requests`：单 SKU 单行、status 仅 `REGISTERED`、无 source/批次/照片/异议/仲裁字段；PRD 03 §3.5 要求**明细列表**（多 SKU）+ 完整流转字段 → V11 需加列或拆明细表；WK 代建的 P1 语义（登记即完成）恰好是 P3 `wk_created` 分支的子集，可平滑扩展
- `outbound_requests`：status 默认 `COMPLETED`；**P1 询价确认 = 同事务建出库单 + 立即 deductStock 扣库存**（`InquiryServiceImpl:224-243`）。PRD 04 §1.2 要求确认后出库单=「待受理」，**扣库存挪到 WK 登记出库时点** → 这是库存语义变更，波及：意向单确认的库存校验改为"确认时校验、登记时扣"（占用/超卖窗口问题）、既有场景测试与 E2E 全部要改。**建议架构评审先定：是否引入"预占库存"或保持确认即扣+状态补拆**
- `inquiry_requests` status 仅 PENDING/CONFIRMED/COMPLETED，无 议价中/已拒绝/已取消/已作废 → R7/R8/R9 需扩（R8 作废联动撤销出库单还要求出库单有可撤状态，同上依赖）
- 反向冲销接口 `InventoryService.reverseInboundForDispute` 仅存在于架构文档，代码无；`deductStock` 有 STOCK_NOT_ENOUGH 硬校验 → **异议冲销若库存已被卖出会失败或打负**（见 §8 风险 1）

### 7.4 单据号 / 状态机 / 调度

- `DocumentNumberServiceImpl`（Redisson RAtomicLong，按日 TTL 重置）与 PRD 05 §7.1 **前缀不一致**（WK-/CK-/XJ- vs IN-/OUT-/IQ-）、**位数不一致**（4 vs 6）；P3 新增 RT/CT/EC 三前缀且 RT 撞角色名 → 需一次性收口（改实现对齐 PRD + 退货改 RTN，或改 PRD 认可现状），存量单据号不回改
- 状态机引擎抽象（StateMachineEngine）为全新构件；现有 3 张单据表的 String 常量 + CAS 更新可保留为引擎底座（引擎=转换表+前置校验+事件发布，不必换存储模型）
- **调度基建缺失**：全仓无 @Scheduled/XXL-Job；72h auto-accept、02:00/02:30 临期任务是 P3 硬依赖，P4（每日快照/月账单）复用 → P3 第一波先立调度选型（建议与架构确认：单体多副本下用 XXL-Job 还是 ShedLock+@Scheduled）

### 7.5 与 P2（开发中）的交叉

- **R14 老单据放行钩子**：P2 强制下架要求"新询价/新出库拒绝、已确认意向单+已生成出库单允许完成"——校验点在 document 域（P2 findings §四已提示跨域）。P3 状态机引擎应把「wholesaler 状态检查」做成统一前置钩子，避免 P2 在 3 处散落 if 后 P3 又推翻
- **R13 退驻前置**"无未结单据"：P3 新增退货/盘点/清库/争议中入库单后，`InventoryService.assertZeroStock` 之外还需 `DocumentService.assertNoOpenDocs` 覆盖新单据类型 → P2 落占位实现时请把单据类型清单做成可扩展枚举
- **WE 授权位**：P2 最小集 2 位，P3 需扩（G7）——P2 的授权位存储设计请预留多位扩展
- **R14 争议中 → 账单**：Wholesaler「争议中」状态位 P2 落，账单标「争议中」是 **P4**；P3 的出库客诉「客诉中」与之无耦合（不改账），但 TA 仲裁入库异议的"补计费"结论要留字段给 P4 回溯（见 G10）

### 7.6 计费依赖标注（P3 → P4 单向）

P3 所有流水必须带**准确的计费语义字段**（类型、生效日、截止日锚点），P4 才能算账：入库次日起算 / 出库·退货·盘亏·清库当日截止 / 盘盈次日起算 / 异议冲销截止异议日 / 仲裁恢复的起算口径（G2 待定）。P3 不实现任何金额计算。

## 八、最大的 3 个未决风险

1. **72h 待确认期的库存可售性与异议冲销矛盾（T1，产品规则空白）**：代建入库"登记即库存+N、正常计费"，即待确认库存立即可被出库/询价占用；但 WA 异议要求"库存即时反向冲销"——若 30 件里已有 20 件被卖出，冲销会把库存打负（或被 `deductStock`/校验拒绝）。PRD 01–05 均未定义"待确认库存是否冻结"。需产品拍板：A. 待确认期冻结不可售（伤代建体验）；B. 可售、冲销按剩余在库封顶+已售差额进 TA 仲裁定责（推荐，与"货已离仓不可逆"哲学一致）。**不定此项，T1 状态机与库存接口都无法冻结设计。**

2. **P1「确认即扣库存直达 COMPLETED」与 P3 完整出库状态机的库存时点冲突（T2/T5，结构性重构）**：PRD 要求扣库存发生在 WK「登记出库」，P1 实现在询价确认瞬间同事务扣减。改时点则确认与出库之间出现超卖窗口，需引入预占/锁定库存概念（PRD 无此概念）；不改则「待受理/已打印/已撤销」状态与库存脱钩、R4/R8 撤回要做反向回补。两条路都触库存域不变量，须在 P3 架构设计第一波收口，且会重写 P1 既有场景测试/E2E。

3. **异常链终点的仲裁能力双双无定义（T1/T2 闭环断点）**：入库链终点=TA 仲裁（线框只有入口无详情、"仲裁通过视同新入库"的计费口径未定）；出库链终点=OPS 仲裁（Q-D04 客诉单字段/流转整体未定义，OPS 端页面全缺，且 OPS 端前端至今全是占位、路由守卫不查角色——P2 findings 已提示）。仲裁不落地，两条异常链就只有"抛出异常"没有"解决异常"。建议 P3 产品设计首个任务即补 Complaint/仲裁 PRD 小节 + 双仲裁线框。
