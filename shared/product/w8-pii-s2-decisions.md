## 1. D1 · wa/Inquiry.vue 询价确认列表"买家电话"列

### 1.1 结论

**放开"查看完整号"按钮**；交互形态**复刻 `ops/TenantAudit.vue` 的 `ElMessageBox.alert` 模式**（点击链接 → 服务端取号 → alert 弹窗展示全号 → 关闭）。

### 1.2 理由

1. **业务必要性**：询价单的终点是"确认并转出库"后的线下交易。WA 需凭买家手机号联系买家确认交付/收款/物流。买家电话是 WA 处理询价单的核心操作信息，不是可有可无的展示字段。
2. **权限已就绪、零后端增量**：`PiiRevealService.revealInquiry`（biz=`INQUIRY`）已实现且与 `InquiryServiceImpl.requireWaRole` 同一权限口径（归属 wholesaler 的 WA 或持 `INQUIRY_CONFIRM` 授权位的 WE）——放开只涉及前端接线（`pii.ts` + 列表列）。
3. **need-to-know 成立**：买家手机号对"该询价单的接收方（WA）"本身就是必要的交易信息，不属于越权扩大。授权位已由服务端复核，无前端自行判断角色带来的绕过风险。
4. **交互一致性**：W7 已上线 `ops/TenantAudit`、`ta/WholesalerApplications` 两处均为"打码 + 查看完整号链接 + alert"模式。WA 端沿用同一模式，降低实现与心智成本；弹窗内联展开需要新增行内状态管理与模板复杂度，且无既有先例，不采用。

### 1.3 影响面

- **前端（W8 实施）**：
  - `wa/Inquiry.vue:263-267` 买家电话列：`{{ row.rtPhone }}` 保持（后端已打码，InquiryServiceImpl:484），列内追加 `查看完整号` 链接按钮，复用 `piiApi.revealPhone('INQUIRY', row.id)`。
  - 权限边界提示：列表对"WE 员工同看本商户询价列表（只读不限授权位，InquiryServiceImpl:397-399）"也可见。未持 `INQUIRY_CONFIRM` 的 WE 点击查看完整号将被服务端 50402 拒绝（toast 提示）。前端不据此隐藏按钮（隐藏需前端读权限位，属过度设计；服务端已兜底）。
- **后端（无需改动）**：INQUIRY biz 已就绪。
- **注意（后端自检）**：`PiiRevealService` 中 `selectInquiryIgnoreTenant` 已定义但 `revealInquiry` 实际调用的是 `inquiryRequestMapper.selectById(id)`（W7 遗留疑点）。若该表受 TenantLine 拦截，WA 查全号可能受租户上下文影响。建议后端在接线时确认（若确认有影响则改用已定义方法，一行改动）。**✅ 2026-09-01 已确认修复**：`inquiry_requests` 确在 `MybatisPlusConfig.TENANT_FILTER_TABLES` 白名单内，WA/WE 登录态下 TenantLine 注入 `tenant_id` 条件、跨租户询价单裸 `selectById` 返回 null → 50401；`revealInquiry` 已改走 `selectInquiryIgnoreTenant(id)`（先 `TenantContext.clear()` 再查、归属校验留在方法内显式完成），main 工作区与 w8-be 工作树两处均已就位，`mvn compile` 验证 PiiRevealService 零编译错误。

### 1.4 交互文案建议

- 列内链接：`查看完整号`（与 TenantAudit/WholesalerApplications 完全一致）
- 弹窗标题：`完整买家电话（询价单 ${docNo}）`（docNo 从 row 取）
- alert 内容：仅展示完整手机号；`确认` 按钮文案 `关闭`
- 无权限/对象不存在：沿用 http.ts 全局 toast，不额外定制

## 2. D2 · wa/PriceSettleDialog.vue 议价沉淀弹窗

### 2.1 结论

**不放开查全号，维持纯打码**。确认 15 号文档 §5.2 的建议（"沉淀专属价只需身份一致性，不需要全号"）。

### 2.2 理由

1. **弹窗用途与全号无关**：弹窗内 3 处 rtPhone 全部服务于"议价/沉淀"身份一致性——
   - `:147` 摘要区"买家 {{ rtPhone }}"：仅标识"这条单是哪个买家的"；
   - `:197` 沉淀提示"写入该买家（{{ rtPhone }}）的客户专属价"：说明归属；
   - `:81` `cp.rtPhone === inq.rtPhone`：逻辑比较，匹配该买家已有专属价。
   任一处的诉求都不是"我需要打电话给这个人"。
2. **联系场景在列表页已满足**：WA 需要联系买家时，在列表页（D1）即可查看完整号；弹窗内再次放开属重复暴露，且弹窗内展示全号没有独立权限/审计意义。
3. **交互成本**：弹窗内再加"查看完整号"会造成"弹窗套弹窗"，收益为零，复杂度上升。

### 2.3 影响面

- **前端**：三处保持现状，**不改**。后端 VO 已打码（InquiryServiceImpl:484），当前展示即打码号 `138****1234`。
- **后端**：无改动。
- **注意（后续）**：V29 明文收缩后，`:81` 的打码号比较仍成立（两端 VO 都走 `SmsUtil.maskPhone`，同一号打码形态一致）。若未来打码口径变化导致比较失效，应由后端改为"服务端身份键比较"再回传布尔，不在本决策范围。

## 3. D3 · wa/Staff.vue 员工手机号：方案 A vs 方案 B

### 3.1 结论

**采用方案 A：保留全号展示（现状），登记为显式例外项**。

### 3.2 理由

1. **数据性质不同**：员工手机号是"自家员工"的内部人事数据，与买家/入驻申请人（外部第三方 PII）性质不同。WA 管理员对自家员工手机号的知情权类比企业 HR 持有员工联系方式——属合理管理需要。
2. **访问者身份唯一、泄露面最小**：员工管理端点后端以 `requireOwnWholesalerId` 校验操作者必须是该商户 ACTIVE 的 WA（`WholesalerEmployeeServiceImpl:152-163`）；页面无 WE 员工可用的管理入口。即全号只暴露给"管理自家员工的那一个人"，不构成跨主体泄露。
3. **方案 B 成本与收益不匹配**：
   - 收益：把"自家员工全号"从列表直接显示改为"点按查看"，观看者仍是同一位 WA 管理员，安全收益接近零；
   - 成本：后端新增 STAFF biz + 权限校验 + 审计分支 + 前端按钮 + 测试 + 验收清单更新，且 WA 每次管理员工（禁用/恢复/授权）都多一次点按摩擦。
4. **与现有豁免先例一致**：本人数据（wa/Apply 回显）、WA 开号（ta/Wholesalers 输入 waPhone）均为明文展示豁免；员工手机号是"管理员看自家员工"，语义最近。

### 3.3 影响面与风险

- **前端**：`wa/Staff.vue:537-541` 保持 `{{ row.phone }}` 全号展示，**不改**。
- **后端**：
  - **V29 收缩前**：`WholesalerEmployeeServiceImpl:201` 直接 `user.getPhone()`，无需改动。
  - **V29 收缩后（W8 收口必做）**：`users.phone` 明文列删除后，员工列表仍要展示全号 → 后端需保证 `WholesalerEmployeeVo.phone` 的解密供给（补 cipher 列后经解密回填，或经 PiiRevealService 解密）。**"方案 A 保留全号"不等于"V29 后裸读明文列"**——这是 W8 后端侧必须补齐的解密路径，建议在 W8 后端任务中显式列为子项。
- **规约登记**：在 guardrails/验收清单中将"WA 员工管理页展示自家员工全号"登记为**显式例外项**（防后续 Agent 误当遗漏修复、也防未来扩展员工页给 WE 时漏改）。
- **风险**：若未来放开"WE 员工也可进入员工管理页/查看同事手机号"，本例外即失效，届时必须改方案 B。当前产品口径**不放开 WE 查看同事手机号**。

## 4. D4 · ta/Pricing.vue 客户端打码过滤残留

> 用户裁决：**移除**（2026-09-01 确认）。

### 4.1 结论

**"移除"对象 = `ta/Pricing.vue:223-236` `fetchCpPage` 中基于打码 rtPhone 的客户端模糊过滤残留**，即删除 `cp.rtPhone.toLowerCase().includes(k)` 任意子串匹配分支与为兼容完整 11 位输入而做的 `maskPhone(kw)` 比较分支（Pricing.vue:227-236）。移除后该选择器**不再按手机号做客户端过滤**，口径与黑名单一致统一为"完整 11 位 → 服务端精确；last4 尾号 → 服务端精确"——但**不新增后端检索端点**（listCustomerPrices 保持无 keyword 参数）。

> 说明（避免执行歧义）：此处的"移除"是**删掉残留的客户端打码过滤逻辑**，不是移除手机号展示/编辑/撤销功能，也不是移除批量调价选择器本身。选择器仍可按 **SKU 名称** 客户端过滤（`fetchSkuPage` 不受影响）；手机号列仅作展示，不再作为客户端搜索键。若业务需要按手机号筛选专属价，由后端按黑名单同口径补检索端点，独立评估。

### 4.2 理由

1. **黑名单 LIKE 下线的口径必然外溢**：W7 已把手机号检索统一为"完整 11 位精确 + last4 尾号精确"（BlacklistServiceImpl:62-74，HMAC 化后 SQL 层不再支持 LIKE）。`ta/Pricing.vue:223-236` 的 `fetchCpPage` 仍保留"基于打码号做任意子串 includes"的模糊匹配残留，语义过宽（输入 `138` 命中所有 138 开头，输入中间段也可命中），与全站检索口径冲突，属**该移除的遗留实现**。
2. **"移除"是口径收敛的最简正解**：既然手机号检索已全局收敛为"11 位精确 + last4"，而该选择器过滤只作用于已全量加载的小数组（单商户专属价通常数百条以内），保留一套"客户端打码号模糊匹配"反而制造维护歧义与口径漂移风险。直接删掉，语义最干净。
3. **选择器仍可用 SKU 名过滤**：`EntityPickerDialog` 的搜索键不止手机号一个——`fetchSkuPage`（Pricing.vue:206-209）按 SKU 名称/规格客户端过滤，满足"批量选专属价"的核心检索诉求（按商品找价）。手机号列仅作展示与复核，不影响选价操作闭环。
4. **不新增后端端点的理由**：若仅因"手机号不能客户端搜了"就为批量调价选择器补后端 keyword 检索（含 hmac/last4 精确查询、分页、接入与测试），成本显著大于收益（选择器数据量小、SKU 过滤已覆盖主场景）。**若未来专属价量级增长、业务确实需要按手机号筛选专属价，再按黑名单同一口径（hmac 精确 + last4）补检索端点**，作为独立需求评估。

### 4.3 实施口径（前端 W8）

- **删除** `ta/Pricing.vue:223-236` `fetchCpPage` 中手机号相关过滤逻辑：
  - 删除 `cp.rtPhone.toLowerCase().includes(k)`（任意子串模糊）；
  - 删除 `maskPhone(kw)` 比较分支（Pricing.vue:227-236）。
- **选择器保留**：`cpPickerColumns`（:211-221）展示列不变；`EntityPickerDialog` 仍展示打码手机号 + SKU + 专属单价 + 状态，供用户浏览/勾选。
- **可选**：若保留选择器搜索能力，仅保留 SKU 名称过滤（对齐 `fetchSkuPage`）；注释同步更新引用 15 §4 阶段2-2 检索口径，明确"手机号不参与客户端过滤"。
- **用户裁决原文**："4、移除"——即移除该客户端打码过滤残留。

### 4.4 影响面

- **前端**：仅 `ta/Pricing.vue:223-236` 的 `fetchCpPage` 手机号过滤分支被移除。列表列（`:647-651` 打码展示）、编辑回填（`:353`，打码号回填 disabled 输入框且提交不含 rtPhone——与 15 §5.2"编辑不回显全号"一致）、撤销确认文案（`:405` 展示打码号）均**保持**。
- **后端**：无改动（不新增检索端点）。
- **后端（W8 收缩衍生 · 2026-09-01 B3 口径确认）**：`customer_prices.rt_phone` 明文列随 W8 删除后，专属价列表打码展示形态统一为 **`****1234`（仅后 4 位）**——新增 `rt_phone_last4 VARCHAR(4)` 摘要列并回填（与 `users.phone_last4`/`sms_codes.phone_last4` 先例一致），VO 直接输出 `****1234`；与黑名单 `PHONE_****1234`、检索口径（11 位精确 + last4）全站一致。**不保留前 3 位形态（`138****1234`）**：该表无全号/号段消费点，保留 prefix 列无业务收益且扩大数据面，明确不加。实现补充：新建（`setCustomerPrice`）与 settle 沉淀（`InquiryServiceImpl` C2 透传）写入时同步维护 last4；V34 删明文列后摘要列保留；回填闸门把 `rt_phone_last4` 回填率纳入；16-pii-w8-shrink-plan §1.6 列清单同步补列。前端零改动（纯字符串渲染 `{{ row.rtPhone }}`，编辑回填 disabled 输入框展示 last4 且提交不含 rtPhone，不受影响）。
- **测试**：批量调价选择器如有按手机号搜索的 E2E 用例，需同步删除/改写（断言不再按手机号过滤、SKU 名过滤仍生效）。
