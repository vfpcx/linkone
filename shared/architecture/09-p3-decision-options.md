## 问题一 · 72 小时待确认库存：能不能卖？异议了怎么冲销？

### 背景

仓库管理员（WK）可以在现场替批发商（WA）直接登记入库——货真实进了仓，系统库存立即增加、仓储费开始计算。批发商随后有 72 小时窗口去「确认」或「异议」这笔代建入库；异议成立时规则要求「库存即时反向冲销」，即把这笔入库在账上抹掉。矛盾在于：这 72 小时里库存已经在系统里，别的零售客户可能已经下单买走了一部分。如果 30 件里已卖出 20 件，此时批发商提出异议要冲销 30 件，账上只剩 10 件，冲销会把库存打成负数（或被系统拒绝）。现有 PRD 对「待确认期库存是否可卖」完全没有定义。

### 问题本质

一句话：**待确认的代建入库库存，是先冻结保证「异议可全额撤回」，还是先放开可卖、异议时只冲销剩余部分？**

### 选项 A · 待确认期冻结，不可售

- **做法**：代建入库的库存单独标记「待确认」，在 WA 确认（或 72h 自动确认）之前，不参与询价、出库、FIFO 拣货；异议时全额冲销，永远不会打负。
- **优点**：账目最干净，异议冲销永远成立；无需仲裁处理「已卖出差额」；实现逻辑简单直观。
- **缺点与风险**：伤代建体验——代建入库的初衷就是「货到了马上能动」，冻结 72h 意味着这批货三天不能卖，试点仓库（本就嫌流程重）可能直接绕开系统线下操作；且与「登记即正常计费」形成「收着钱却不让卖」的观感矛盾。
- **开发量**：中。库存表需增加「冻结/可用」二段余额（或独立冻结池），询价确认、出库校验、FIFO 三处都要感知冻结量；确认/72h 到点再解冻。

### 选项 B · 可售；异议冲销按「剩余在库」封顶，已售差额进 TA 仲裁定责（预研推荐）

- **做法**：待确认库存与正常库存无差别可售。WA 异议时，系统只冲销当前还在库的部分（例：登记 30 件、已卖 20 件，则冲销 10 件），已卖出的 20 件差额自动记入异议单，交由店长（TA）仲裁定责、线下解决赔偿。
- **优点**：与「货已离仓不可逆」的既有平台哲学一致（出库链就是这么定的）；代建体验不受损，货到即可卖；库存永不打负，冲销逻辑确定。
- **缺点与风险**：异议方（WA）可能不满「我还没确认的货被卖了」，需在产品文案上明示「代建入库即视为可售，72h 内可提异议但仅覆盖在库部分」；TA 仲裁多了一类「差额定责」场景，仲裁 PRD（见问题三）要包含它。
- **开发量**：小到中。无需冻结池；核心是异议冲销接口按剩余在库封顶 + 异议单记录差额字段；比选项 A 少改询价/出库/FIFO 三处。

### 选项 C · 可售，但「一旦动销视同确认」

- **做法**：待确认库存可售；但只要发生任何一笔出库/售出，该入库单自动转「已确认」，异议窗口提前关闭（未动销的仍保留 72h 窗口）。
- **优点**：彻底消灭「冲销与已售并存」的矛盾场景；逻辑上自洽（你都开始卖了，等于认了这批货）。
- **缺点与风险**：对 WA 最不友好——WA 可能根本不知道货被卖了就失去了异议权（尤其 FIFO 自动拣到这批货时，动销并非 WA 主动行为）；容易引发「系统替我做了决定」的投诉；边界多（部分动销算不算整单确认？）。
- **开发量**：中。出库/拣货链路要回写入库单状态，跨域事件多一条。

### 预研推荐

预研明确推荐**方案 B**：可售 + 冲销按剩余在库封顶 + 已售差额进 TA 仲裁定责，理由是与「货已离仓不可逆」的既有哲学一致（08 预研 §8 风险 1）。

### 不决策的后果

T1 入库异常链的状态机与库存冲销接口（`reverseInboundForDispute`）无法冻结设计，**P3 第一波（入库异常链 + 库存流水扩展）整体不能开工**；同时问题三的 TA 仲裁 PRD 也依赖本题结论（是否含「差额定责」场景）。

## 问题二 · 扣库存的时点：询价确认时扣，还是仓库实际出库时扣？

### 背景

P1 已上线的卖货闭环里，为了流程最短，采取了「批发商确认询价单的那一瞬间，系统同时生成出库单并立刻扣减库存」的做法——出库单生下来就是完成态。而 PRD 为 P3 设计的完整出库流程是：确认询价后出库单先处于「待受理」，仓库打印拣货、实际把货搬出去登记时才扣库存，中间还允许撤回、作废。两者的核心分歧是**库存在哪个环节减掉**：改成 PRD 的时点，确认到出库之间就存在一个「别人可能把同一批货也买走」的超卖窗口；不改，则出库单的中间状态（待受理/已打印）与库存实况脱节，撤回时要做反向回补。这直接决定 P3 单据状态机的地基怎么打，且无论选哪条路，P1 的既有测试都要跟着重写一部分。

### 问题本质

一句话：**确认与实际出库之间的那段时间，这批货在账上算「已扣」「预占」还是「仅校验过」？**

### 选项 A · 按 PRD 改为出库登记时扣，引入「预占库存」

- **做法**：询价确认时不扣库存，只把对应数量标为「预占」（可用库存 = 在库 − 预占）；WK 实际出库登记时把预占转为真实扣减；撤回/作废即释放预占。
- **优点**：与 PRD 状态机完全一致，账实相符（货还在仓，库存就还在，只是不可再卖）；不存在超卖窗口；撤回/作废逻辑最干净（释放预占即可，无需反向流水）。
- **缺点与风险**：引入 PRD 里原本没有的「预占」概念，库存模型从一段式变两段式，波及询价校验、FIFO 拣货、盘点口径（盘点盘的是在库数还是可用数？需连带定义）、以及问题一若选 B 时的「剩余在库」口径；P1 既有场景测试与 E2E 全部要改。
- **开发量**：大。库存域结构性改造 + 全链路回归。

### 选项 B · 保持「确认即扣」，状态机补拆（扣减时点不动）

- **做法**：库存仍在询价确认瞬间扣减；P3 只把出库单从「直达完成」拆出 待受理→已打印→已出库 的中间状态（记录仓库作业进度）；撤回（R4）/意向单作废联动（R8）时生成一条反向回补流水把库存加回来。
- **优点**：不动 P1 已验证的库存语义，无超卖窗口，改造面最小；中间状态纯粹是作业流程记录，风险可控；反向回补流水与问题一的「冲销走独立流水」原则（D22）同构，审计链一致。
- **缺点与风险**：与 PRD 04 §1.2 字面不符，需产品修订 PRD 认可「确认即扣」口径；账实有窗口期偏差（货还在仓但账上已减），盘点若撞上「已确认未出库」单据需口径说明；撤回高频时反向流水会变多（可接受，均有据可查）。
- **开发量**：小到中。状态机拆分 + 反向回补流水 + PRD 修订；P1 测试小改。

### 选项 C · 改为出库登记时扣，但不做预占（确认仅校验）

- **做法**：确认时只校验库存充足不扣不占；实际出库登记时再扣，若届时不足则拒绝出库并通知。
- **优点**：实现最简单，字面上也符合 PRD 时点。
- **缺点与风险**：**超卖窗口真实存在**——两个客户可先后确认同一批货，仓库发第二单时才发现没货，履约失败发生在客户已确认之后，商誉损失最大；平台型业务通常不可接受。
- **开发量**：小，但业务风险最高，列出仅为完整性。

### 预研推荐

预研未给出单一倾向，原文要求「**P3 架构设计第一波必须收口**：是否引入预占库存，或保持确认即扣 + 状态补拆」（08 预研 §7.3、§8 风险 2）。即真实候选是 A 与 B 二选一；C 因超卖风险不建议。若以「改造面最小、不引入 PRD 外新概念」为准绳，B 更稳妥；若以「账实相符、状态机严格遵循 PRD」为准绳，选 A 并接受库存域重构。

### 不决策的后果

T5 单据状态机引擎、T2 出库异常链（R4 撤回、R8 作废联动、代建出库、客诉）全部无法定稿——**P3 架构第一波（状态机引擎 + 出库改造）被阻塞**；且问题一选 B 时「剩余在库」的计算口径也悬而未决。

## 问题三 · 两条异常链的终点：仲裁怎么落地？

### 背景

P3 的两条异常处理链，终点都是「仲裁」：入库链——批发商异议代建入库后由店长（TA）仲裁，裁定异议是否成立、库存流水是否恢复；出库链——批发商对代建出库不可异议，只能 30 天内提「客诉」，由平台运营（OPS）仲裁，仅判责不改库存与账单。目前两个终点都没有可开发的定义：TA 仲裁只有入口没有详情页与结论选项，「仲裁通过视同新入库」的计费口径也没说清；OPS 这边更空——客诉单（Complaint）这个单据本身的字段与流转就没定义过（未决问题 Q-D04），OPS 端页面全缺。仲裁不落地，两条异常链就只有「抛出异常」没有「解决异常」，等于给了用户一个投诉按钮但永远没有下文。

### 问题本质

一句话：**P3 是把双仲裁完整做出来、做一个最小闭环版，还是先只挂「处理中」状态把仲裁推到 P5？**

### 选项 A · P3 首个产品任务补齐 PRD，双仲裁完整落地

- **做法**：P3 产品设计第一件事就是补 Complaint 实体 + TA/OPS 双仲裁 PRD 小节与线框（含调证、沟通记录、多轮处理），随对应波次完整开发。
- **优点**：两条异常链一次闭环，无欠账；OPS 端从占位变可用。
- **缺点与风险**：客诉/仲裁的「完整版」（调证流程、多轮沟通、证据管理）设计工作量大且试点期数据少、需求不明，容易过度设计；拖慢 P3 主链进度。
- **开发量**：大（含 OPS 前端从零起）。

### 选项 B · 最小闭环版：仲裁 = 单据引用 + 理由 + 附件 + 结论枚举 + 双方通知（预研 G3 方向）

- **做法**：P3 开工时先补最小 PRD——Complaint/仲裁单只含：关联单据、发起理由、附件照片、结论（入库仲裁：通过恢复流水 / 驳回保留冲销；出库客诉：WK 责任 / WA 责任 / 双方协商 / 无责，此四选枚举 PRD 已有）、结论备注、双方站内信通知。TA 仲裁复用现有审批中心弹窗样式；OPS 端做一个简单列表 + 结论弹窗。调证、多轮沟通、赔偿追踪等一律 P5 再议（平台本就不接资金，结论仅作线下依据）。
- **优点**：两条链在 P3 就有终点、能闭环验收；设计与开发量可控；与「平台不接资金、仲裁只判责」的既定原则匹配，最小版已覆盖 90% 试点场景。
- **缺点与风险**：复杂纠纷（需多轮举证）体验简陋，靠线下沟通兜底；P5 扩展时可能小幅返工列表/详情页。
- **开发量**：中。需同步敲定：仲裁通过「视同新入库」的计费起算日（建议：恢复流水沿用原入库时间戳、计费语义字段标注给 P4 回溯——预研 G10 口径），及问题一选 B 时的「差额定责」展示。
- **前置小项**：Q-D04 客诉单实体按此最小集一并收口。

### 选项 C · 仲裁整体延到 P5，P3 只落「争议中 / 客诉中」状态

- **做法**：P3 只实现异议冲销与客诉提交，单据停在「争议中/客诉中」，页面提示「请线下联系处理」；仲裁功能 P5 交付。
- **优点**：P3 工作量最小，主链（单据状态机、批次）最快。
- **缺点与风险**：异常链有头无尾——单据可能长期停留在争议态；「争议中」单据会卡退驻前置校验（无未结单据）等 P2 已落规则；用户观感差（能投诉、无人处理的系统）。
- **开发量**：最小，但产品完成度风险最高。

### 预研推荐

预研倾向明确：「建议 P3 产品设计**首个任务**即补 Complaint/仲裁 PRD 小节 + 双仲裁线框」（§8 风险 3），且缺口清单 G3 给出「可最小化：单据引用+理由+附件+结论四选+双方通知」——即**选项 B 的最小闭环路线**（时序上采纳 A 的「首个任务先补 PRD」，范围上采纳最小集）。另注：预研提到的「OPS 路由守卫不查角色」已在 feat/p2-onboarding-fe 修复（Team Lead 2026-07-16 修正），OPS 端落地障碍比预研描述小一档。

### 不决策的后果

T1 入库异常链、T2 出库异常链**双双无法闭环验收**（有异议/客诉入口、无处理出口）；Q-D04 持续悬置；若拖到波次中期再定，仲裁字段要回补进已定稿的单据表结构，返工成本更高。

## 已知口径修正（随本次一并确认，非三大风险但需表态）

### 修正一 · 单据号：PRD 与已上线实现冲突

- **现状**：PRD 05 §7.1 规定 `IN-/OUT-/IQ-` 前缀 + 6 位日内序列（如 `IN-CC01-20260520-000123`）；但 P1 已上线并产生存量单据的实现是 `WK-/CK-/XJ-` 前缀 + 4 位日内序列（如 `WK-T8801-20260629-0007`，`DocumentNumberServiceImpl`）。P3 还要新增退货/盘点/清库三种前缀，其中 PRD 的退货前缀 `RT-` 与零售终端角色缩写 RT 撞名。
- **建议**：**按已上线实现为准，修订 PRD**——存量单据号已打印在纸质单据上不可回改，改实现迁就 PRD 得不偿失；4 位日序（单仓单日 9999 单）对试点远够。P3 新前缀沿用同格式，退货前缀避开撞名改 `RTN-`（或 `TH-`）。同时把 Q-D10「序列按日重置（key 带日期 + 当日 TTL）」作为正式口径写回 05 §7.1。
- **如不同意**（坚持 PRD 格式）：需一次性改实现 + 明确存量单据号不回改的双格式共存说明，开发量小但对账/客服要背两套格式，不推荐。

### 修正二 · Flyway P3 起始版本号（已实测）

- **实测现状（2026-07-23）**：main 分支 `backend/src/main/resources/db/migration/` 现有 **V1–V13**（V13 为 `application_pending_unique`）；Wave6 缺陷修复分支（fix/p2-defects，worktree defects-be）已占用 **V14**（`V14__merge_wa_placeholder_role.sql`），待合并 main。
- **口径**：预研写的「P3 从 V11 起」与 Team Lead 7-16 修正的「从 V12 起」**均已过期**。**P3 迁移从 V15 起编号**；P3 各波开工前须再核一次 main 及在途分支最高版本号（P2 收尾仍在进行）。

### 修正三 · 预研中其他已被修正的过期信息（备忘）

- 「OPS 路由守卫不查角色」已修复（见问题三预研推荐末注），P3 以 P2 合并后代码为准。
